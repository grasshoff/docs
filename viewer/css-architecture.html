CSS Architecture - AI PDF Scholar Viewer

Overview

The viewer now uses external CSS files for document content styling, separating concerns between: - Inline CSS: Viewer UI (navigation, panels, controls) - External CSS: Document content formatting (paragraphs, footnotes, typography)

File Structure

ai-viewer/
├── application/
│   └── main_viewer.html        # Main viewer (inline UI CSS only)
├── config/
│   ├── README.md               # Configuration documentation
│   └── styles/
│       └── document-content.css # Document content styling
└── docs/
    └── css-architecture.md     # This file

CSS Organization

1. Inline CSS (main_viewer.html)

Purpose: Viewer UI components and layout

Includes: - Navigation bar styling - Panel layout (dual-pane) - Control buttons - Loading/error states - Glass-morphism effects - Document selection page

Why inline? - Critical rendering path optimization - Viewer UI is tightly coupled to HTML structure - Reduces HTTP requests for initial load

2. External CSS (config/styles/document-content.css)

Purpose: Document content formatting

Includes: - Paragraph spacing and typography - Footnote styling (inline refs + bottom section) - Section headers - Paragraph numbers (<parno>) - Mathematical content - Heading hierarchy

Why external? - Customizable: Users can edit without touching HTML - Reusable: Same styles across different viewers - Version control: Style changes tracked separately - Extension-ready: Easy to package for VSCode/Cursor

Usage

Loading External CSS

<!-- In main_viewer.html -->
<link rel="stylesheet" href="../config/styles/document-content.css">

Customizing Styles

  1. Edit document content styles:

    vi config/styles/document-content.css

  2. Refresh browser (no rebuild needed)

  3. Commit changes:

    git add config/styles/document-content.css
git commit -m "Update paragraph spacing"

Adding New Styles

For new document-specific styles:

  1. Add to config/styles/document-content.css
  2. Target semantic XML tags (<p>, <fn>, <section>, etc.)
  3. Use namespaced classes (.text-content .your-class)

CSS Selectors

Document Structure

The OCR XML is rendered with this structure:

<div class="text-content" id="textContainer">
    <page pidx="21">
        <meta .../>
        <header>...</header>
        <main>
            <p>Paragraph content</p>
            <section>Section header</section>
            <p><parno>31.</parno> Paragraph with number</p>
            <p>Text with footnote<fn>7</fn></p>
        </main>
        <footnote>
            <fn>[^7]: Footnote text</fn>
        </footnote>
    </page>
</div>

Key Selectors

/* Paragraphs */
.text-content p { }

/* Inline footnote references */
.text-content fn { }

/* Footnote section */
.text-content footnote { }

/* Individual footnote entries */
.text-content footnote fn { }

/* Section headers */
.text-content section { }

/* Paragraph numbers */
.text-content parno { }

/* Headings */
.text-content h1, h2, h3 { }

JavaScript Enhancements

Some styling is applied via JavaScript for dynamic content:

// In loadText() function
const paragraphs = container.querySelectorAll('p');
paragraphs.forEach(p => {
    const text = p.textContent.trim();
    // Add extra spacing for numbered paragraphs (e.g., "20.")
    if (/^\d+\./.test(text)) {
        p.style.marginTop = '2.5em';
    }
});

VSCode/Cursor Extension

Extension Structure

Configuration API

// settings.json contribution
"ai-pdfscholar.viewer": {
  "fontFamily": "Crimson Text, Georgia, serif",
  "paragraphSpacing": 1.5,
  "footnoteStyle": "bottom-border",
  "theme": "default"
}

User Overrides

Users can override styles in workspace settings:

// .vscode/settings.json
{
  "ai-pdfscholar.viewer.customCSS": "${workspaceFolder}/.ai-viewer/custom.css"
}

Benefits of External CSS

  1. Separation of Concerns
    • UI styling separate from content styling
    • Easier to maintain and update
  2. Customization
    • Users can modify without touching HTML
    • No need to understand JavaScript
  3. Version Control
    • Style changes tracked separately from logic
    • Easy to revert or compare changes
  4. Testing
    • Can test different styles without rebuilding
    • A/B testing different typography
  5. Extension Support
    • Clean structure for extension packaging
    • Standard VSCode configuration patterns
  6. Performance
    • Browser caching of external CSS
    • Can be minified separately

Best Practices

  1. Keep inline CSS for UI only
    • Navigation, panels, controls
    • Critical above-the-fold content
  2. Use external CSS for content
    • Typography, spacing, colors
    • Document-specific formatting
  3. Namespace all selectors
    • Use .text-content prefix
    • Avoid global styles
  4. Comment extensively
    • Explain purpose of each section
    • Document any magic numbers
  5. Test across documents
    • Mathematical content
    • Historical texts
    • Different languages

Maintenance

Adding New Styles

  1. Identify the XML structure
  2. Add selectors to document-content.css
  3. Test with multiple documents
  4. Document in comments

Updating Existing Styles

  1. Check impact on all document types
  2. Update comments if behavior changes
  3. Test with numbered paragraphs, footnotes, etc.

Performance Considerations

  • Keep selectors simple and efficient
  • Avoid overly specific selectors
  • Use CSS containment where appropriate
  • Monitor rendering performance

# CSS Architecture - AI PDF Scholar Viewer

## Overview

The viewer now uses **external CSS files** for document content styling, separating concerns between:
- **Inline CSS**: Viewer UI (navigation, panels, controls)
- **External CSS**: Document content formatting (paragraphs, footnotes, typography)

## File Structure

```
ai-viewer/
├── application/
│   └── main_viewer.html        # Main viewer (inline UI CSS only)
├── config/
│   ├── README.md               # Configuration documentation
│   └── styles/
│       └── document-content.css # Document content styling
└── docs/
    └── css-architecture.md     # This file
```

## CSS Organization

### 1. Inline CSS (`main_viewer.html`)

**Purpose**: Viewer UI components and layout

**Includes**:
- Navigation bar styling
- Panel layout (dual-pane)
- Control buttons
- Loading/error states
- Glass-morphism effects
- Document selection page

**Why inline?**
- Critical rendering path optimization
- Viewer UI is tightly coupled to HTML structure
- Reduces HTTP requests for initial load

### 2. External CSS (`config/styles/document-content.css`)

**Purpose**: Document content formatting

**Includes**:
- Paragraph spacing and typography
- Footnote styling (inline refs + bottom section)
- Section headers
- Paragraph numbers (`<parno>`)
- Mathematical content
- Heading hierarchy

**Why external?**
- **Customizable**: Users can edit without touching HTML
- **Reusable**: Same styles across different viewers
- **Version control**: Style changes tracked separately
- **Extension-ready**: Easy to package for VSCode/Cursor

## Usage

### Loading External CSS

```html
<!-- In main_viewer.html -->
<link rel="stylesheet" href="../config/styles/document-content.css">
```

1. Add to `config/styles/document-content.css`

## Benefits of External CSS

1. **Separation of Concerns**
   - UI styling separate from content styling
   - Easier to maintain and update

2. **Customization**
   - Users can modify without touching HTML
   - No need to understand JavaScript

3. **Version Control**
   - Style changes tracked separately from logic
   - Easy to revert or compare changes

4. **Testing**
   - Can test different styles without rebuilding
   - A/B testing different typography

5. **Extension Support**
   - Clean structure for extension packaging
   - Standard VSCode configuration patterns

6. **Performance**
   - Browser caching of external CSS
   - Can be minified separately

## Best Practices

1. **Keep inline CSS for UI only**
   - Navigation, panels, controls
   - Critical above-the-fold content

2. **Use external CSS for content**
   - Typography, spacing, colors
   - Document-specific formatting

3. **Namespace all selectors**
   - Use `.text-content` prefix
   - Avoid global styles

4. **Comment extensively**
   - Explain purpose of each section
   - Document any magic numbers

5. **Test across documents**
   - Mathematical content
   - Historical texts
   - Different languages

## Maintenance

### Adding New Styles

1. Identify the XML structure
2. Add selectors to `document-content.css`
3. Test with multiple documents
4. Document in comments

### Updating Existing Styles

1. Check impact on all document types
2. Update comments if behavior changes
3. Test with numbered paragraphs, footnotes, etc.

### Performance Considerations

- Keep selectors simple and efficient
- Avoid overly specific selectors
- Use CSS containment where appropriate
- Monitor rendering performance
